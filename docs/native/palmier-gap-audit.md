# Capability audit — vii native editor vs. palmier-pro

> Generated by a 9-agent ultracode audit (7 domain auditors + roadmap synthesis + completeness critic),
> reading palmier-io/palmier-pro's Swift/Metal source directly against our Rust/GPUI crates.
> Scope excludes palmier-pro's AI-assistant surface (Agent, Generation, Account, MCP server).

## Headline

The gap is large but lopsided: our GPU/engine core is genuinely strong (reversible ProjectPatch undo with 23 tests, a pure view model, a 17-mode WGSL blend shader and a JFA mask-feather pipeline that palmier has no equal of) while the layer above it is a demo. The blocking problem is not missing features, it's that the data model cannot express what a video editor needs — `Transform` has one uniform `scale` (so every non-16:9 source is stretched today), trims never write `trim_start`/`trim_end`, `AudioElement` has no trim/animations, `VideoElement` has no volume, `Element` has no blend/crop, and `Effect.params` is `BTreeMap<String,f32>` against a fixed 8-float uniform buffer. Three runtime pipelines are prototypes that must be rewritten rather than extended: audio (decode-whole-file-then-mix-whole-timeline on the UI thread), video decode (whole-clip RAM cache hard-capped at 320×180/450 frames, so any clip over ~15s is simply wrong), and export (blocking, silent, fixed path, force-downscaled to 1280px). Fix the model and those three pipelines first; a surprising amount of palmier parity is then wiring, not invention.

## Where we are already ahead

- 17-mode blend compositing is fully implemented and GPU-tested in WGSL — `compositor::BlendMode` (rust/crates/compositor/src/blend_mode.rs) covers all modes including the non-separable hue/saturation/color/luminosity set, exercised by rust/crates/compositor/tests/native_gpu.rs. Palmier dispatches to CoreImage blend filters per layer. Ours is unreachable only because `Element` has no `blend_mode` field and opencut-preview hardcodes `BlendMode::Normal` (lib.rs:346) — the highest value-per-line item in the whole roadmap.
- A jump-flood (JFA) signed-distance-field mask feather pipeline exists and has no palmier equivalent: rust/crates/masks/src/{sdf.rs, feather.rs} plus jfa_init/jfa_step/jfa_distance WGSL, wired into `render_layer` behind `LayerMaskDescriptor {texture_id, feather, inverted}`. Palmier's nearest equivalents are a corner-rounding kernel and CIBlendWithMask. Ours is dead code purely because opencut-preview always emits `mask: None` (lib.rs:348) — the single most under-exploited asset in the repo.
- Undo/redo is architecturally cleaner: self-inverting `ProjectPatch` mutations with `Lowered.forward: Vec<ProjectPatch>` and 23 tests in opencut-core. Palmier leans on AppKit's UndoManager plus `withTimelineSwap`, which snapshots and restores the entire timeline for complex ripples. Our patch model can express multi-element single-undo edits without whole-document snapshots — we just have not written a Command that uses it yet.
- Clean headless separation: opencut-core is a pure engine (Command / ProjectPatch / EventBus) with no UI dependency, and opencut-ui/src/view_model.rs is pure and unit-tested. Palmier's EditorViewModel is a @MainActor SwiftUI object with editing policy, keyframe logic, ripple policy and multicam rules fused into the view layer. Every pure planner we port (snap, overwrite, ripple, silence-removal, caption chunking) lands in a testable crate rather than a view controller.
- Cross-platform GPU stack: wgpu + WGSL across gpu/compositor/effects/masks, versus palmier's Metal + CoreImage + AVFoundation lock-in. Their entire compositing, playback and export path is macOS-only by construction; ours is portable, and wgpu additionally gives us real `TextureDimension::D3` so 3D LUTs can be done cleaner than palmier's 2D n×n² strip hack.
- We have a second, mature implementation to port from that palmier does not: apps/web (the original OpenCut) already ships a full snapping subsystem (element/playhead snap sources, group-move snap, snap indicator, enable toggle), a ripple engine (src/ripple/{diff,shift,apply}.ts), an audio gain-automation model with dB scaling and a proper master limiter (src/media/audio-mastering.ts), preview hit-test + transform handles + preview snapping (~1600 lines), a params registry, subtitle SRT/ASS import, and a waveform cache. Several of these are strictly richer than palmier's version.
- Keyframe interpolation prior art is ahead of the target: apps/web/src/animation/types.ts models `linear | hold | bezier` with `CurveHandle {dt,dv}`, TangentMode (auto/aligned/broken/flat), channel extrapolation modes and grouped property channels. Palmier ships only linear/hold/smoothstep. Porting our own web model beats copying theirs.
- Time model is more precise: integer `MediaTime` at 120,000 ticks/sec plus rational `Fps {numerator, denominator}` in opencut-project/src/settings.rs, versus palmier reasoning in Int frames throughout. Better foundation for mixed-frame-rate timelines and drop-frame timecode — though nothing currently quantizes to it, which is its own Wave 1 item.
- Recent native-path work already landed that palmier gets for free from AVFoundation but that we now control explicitly: hardware-accelerated decode (`-hwaccel auto`), cached text rasters, native-order preview readback, and multi-clip audio mixing (commits b382c9b, f7d278b, e054da1).

## Architectural prerequisites

These block large parts of the roadmap; several are live correctness bugs today.

- Transform must gain independent width/height (plus source natural size) instead of one uniform `scale`. rust/crates/opencut-project/src/element.rs:83-89 is `{x,y,scale,rotation,opacity}`, so opencut-preview/src/lib.rs:334-344 emits `width: scale*canvas_w, height: scale*canvas_h` for every layer — a 16:9 clip and a square image are both stretched to the canvas box. This is a live rendering bug and a hard blocker for corner-resize, crop, aspect-correct hit testing and letterboxing.
- Trims must write source in/out points. `Command::TrimElement` (rust/crates/opencut-core/src/command.rs:68-72) sets start+duration only; `trim_start` is written just once at element creation even though the renderer reads it (opencut-preview/src/lib.rs:311). `AudioElement` (element.rs:157-165) has no trim fields at all, so left-trimming or splitting audio slides the clip in time while both halves still replay from source 0. Needs a `ProjectPatch::SetElementTrim` and trim fields on AudioElement; blocks slip/slide/roll and every ripple path, which reason in source frames.
- opencut-core needs (a) batched, named undo transactions and (b) an apply/revert/commit triad for transient edits. `Editor::execute` records exactly one history entry per Command, and no Command touches more than one element — so a multi-clip move, a ripple across tracks, or any live drag (canvas transform, slider, colour wheel, font hover-preview) would flood history with N entries. `Lowered.forward: Vec<ProjectPatch>` already supports many-element single-undo, so the plumbing exists; the wrapper does not. Roughly eight downstream items assume both.
- Multi-element commands must exist before ripple/overwrite/cross-track drag. `ElementRef` embeds the track id, so `Command::MoveElement` can never relocate a clip to another track; there is no shift/push primitive and no multi-range removal. Needs e.g. `MoveElements { moves: Vec<(ElementRef, track_id, MediaTime)> }` plus pure planner modules (overwrite.rs, ripple.rs) mirroring palmier's OverwriteEngine/RippleEngine action shape.
- The effect system needs a declarative registry AND a richer param/pass model before any grading work is feasible. Today one effect is hardcoded in four places (shader map + `pack_effect_uniforms` in rust/crates/effects/src/pipeline.rs, `effect_groups()` in opencut-preview/src/lib.rs:24-64, a 4-entry button array in editor_view.rs, and a single `amount` stepper in view_model.rs:170). Three structural limits confirmed in source: `EffectUniformBuffer` is fixed at `resolution[2] + direction[2] + scalars[4]` (pipeline.rs:53-58) so a 9-param colour wheel cannot fit; the bind-group layout binds exactly one input texture, so LUTs and 1D curve LUTs have nowhere to go; and `apply_with_encoder` chains passes strictly linearly with one input each, so multi-input composites (glow, clarity) are inexpressible. `Effect.params: BTreeMap<String,f32>` also has no string variant (blocks LUT paths and curve JSON) and no keyframe track (no effect param can be animated), and `effect_groups()` never receives the playhead so nothing time-varying (e.g. animated grain) can be sampled.
- Audio playback must become a streaming mixer. Today `toggle_play` synchronously ffmpeg-decodes every referenced media in full on the GPUI thread, then mixes the entire remaining timeline into one Vec<f32> for a rodio sink (editor_view.rs:204-300, opencut-audio/src/lib.rs:14-38). Consequences: Play stalls for seconds on first press, ~352 KB/timeline-second of mix buffer plus an unbounded never-evicted PCM cache, the mix is frozen at Play time so edits are inaudible until stop/start, scrubbing is silent, and the playhead advances on wall-clock `Instant` deltas while rodio plays off the device clock so A/V drift is unbounded with no resync. Blocks scrub audio, meters, playback rate, and live mix edits.
- Video decode must become windowed/streaming. `decode_video_clip` (opencut-preview/src/lib.rs:379-423) pre-decodes a whole clip into RAM at a hardcoded 320×180/30fps and hard-caps at VIDEO_MAX_FRAMES = 450, and each displayed frame is re-uploaded as a fresh GPU texture (lib.rs:320-329). Clips longer than ~15s or wider than 320px are wrong today, independent of any feature work.
- Export must move off the GPUI thread and gain an options model. `export_video` (opencut-preview/src/lib.rs:191-246) is one fixed ffmpeg invocation with `-pix_fmt yuv420p` and no codec/bitrate/quality flags, no second input, no `-map`, no audio codec; the caller force-scales to max 1280px wide (editor_view.rs:664-666) so a 1080p project always exports 720p; the return bool is discarded (`let _ = renderer.export_video(...)`), so there is no progress, cancel, or error path and the UI freezes for the whole encode.
- Media needs probing and a manifest. `MediaAsset` is `{id, name, path}` (opencut-project/src/project.rs:21-25) with an absolute path and no duration/dimensions/fps/hasAudio, so `import_media` hardcodes `MediaTime::from_ticks(TICKS_PER_SECOND * 4)` (editor_view.rs:564) for every file — a 3-minute clip imports as a 4-second clip with trim_end also 4s. Blocks correct import, duration sort, project portability, relink, and well-formed FCPXML.
- The preview render size must follow the project canvas aspect and the panel size. It is hardcoded PREVIEW_RENDER_W/H = 640×360 into a fixed 512×288 div (editor_view.rs:20-21, 1084-1085), so a 9:16 project renders letterboxed into a 16:9 buffer. A `videoContentRect` equivalent is a prerequisite for viewer hit-testing coordinate mapping and for canvas zoom.
- Known constraint, not a prerequisite: zero-copy GPU→GPUI stays blocked because GPUI 0.2.2 renders on blade-graphics, not wgpu (per the recorded `gpui-uses-blade-not-wgpu` finding). The CPU readback in `PreviewRenderer::render` stays for now — which makes render-size adaptivity and a reduced-quality scrub tier the highest-leverage perf levers instead.

## Ranked roadmap

### Wave 1 — Broken without it

These are not feature gaps, they are places where the editor produces wrong output, makes a core loop impossible, or blocks most of the rest of the roadmap. Four of them (Transform aspect, source trim, batched undo, media probe) are cheap model fixes that unblock roughly two-thirds of Waves 2-3, so they should land before any UI work. Three are pipeline rewrites (audio mixing, video decode, export) that get more expensive the longer we build on top of the prototypes. Ordering within the wave matters: items 1-4 first, then the timeline/transport basics, then the pipelines.

| Effort | Item | Domain | Why |
|---|---|---|---|
| M | **Media import is wrong: probe real metadata and show a real media library** | media | Two verified defects compound. `import_media` hardcodes `MediaTime::from_ticks(TICKS_PER_SECOND * 4)` (editor_view.rs:564) for video, audio and image alike, so a 3-minute clip lands on the timeline as a 4-second clip with trim_end also 4s — importing any real footage produces a wrong clip. And `media_panel()` renders a hardcoded 3-element array (`("media-clip","Clip.mp4"), ("media-logo",...), ("media-music",...)` at editor_view.rs:979-981) and never reads `editor.media()`, so imported assets are invisible and cannot be re-added without re-importing. Palmier's MediaAsset.loadMetadata() probes duration/dimensions/fps/hasAudio and persists them in MediaManifestEntry; MediaTab renders the real asset list. ffprobe via our existing ffmpeg-sidecar dependency covers the probe in one call. Prerequisite for duration sort, correct trims, project settings matching and well-formed FCPXML. |
| M | **Transform: independent width/height + source natural size** | engine/model | `Transform {x, y, scale, rotation, opacity}` (opencut-project/src/element.rs:83-89) has one uniform scale, so opencut-preview/src/lib.rs:334-344 emits `width: scale*canvas_w, height: scale*canvas_h` for every layer. Every source whose aspect differs from the canvas is stretched right now, with no letterboxing and no notion of natural size. Palmier's Transform is topLeft + width + height + rotation in normalized units, and CompositionBuilder additionally stores each clip's preferredTransform and natural size so resizes stay aspect-correct. Hard blocker for canvas corner-resize (meaningless while w and h are the same number), for crop, and for aspect-correct viewer hit testing. Animation channels keyed "scale" need the new components too. |
| S | **Trim must move the source in/out point (and audio must have trim at all)** | engine/model | `Command::TrimElement` (command.rs:68-72) lowers to SetElementStart + SetElementDuration only, and `trim_start` is written just once at element creation (editor_view.rs:594, L1010) despite the renderer reading it (opencut-preview/src/lib.rs:311) — so a left-edge trim slides the clip while still showing the same source frames, and trims are not capped by available media. Worse, `AudioElement` (element.rs:157-165) has no trim_start/trim_end at all; editor_view.rs derives `src_start_secs` from the playhead, so trimming audio moves it in time without cutting into it and SplitElement yields two halves that both replay from source 0. Palmier captures source headroom up front (DragState.TrimDrag + trimHeadroom()) and commits through trimClipInternal, which writes trimStartFrame/trimEndFrame alongside startFrame/duration. Needs `ProjectPatch::SetElementTrim` and a no-source-media branch for image/text. Correctness bug first, parity second — and it blocks slip/slide/roll and every ripple path. |
| S | **Batched named undo transactions + an apply/revert/commit primitive for live edits** | engine/core | `Editor::execute` records exactly one history entry per Command and no Command touches more than one element, so every future multi-clip move, ripple, or drag becomes N undo entries; history also carries only `CommandKind` with no human-readable label. Separately there is no transient-edit path, so any live drag (canvas move/resize, a slider, a colour wheel, a font hover-preview, a chroma eyedropper that temporarily disables the existing key) has nowhere to live. Palmier has both: `EditorUndo.perform(actionName){...}` groups a whole gesture into one named entry, and every mutation has an `apply*` (live, no entry) / `commit*` (one entry) pair. Cheap now, expensive later — roughly eight items in Waves 1-2 assume both exist. `Lowered.forward: Vec<ProjectPatch>` already supports the many-patch half. |
| M | **Timeline ruler, draggable playhead, click-to-seek, frame-accurate transport and timecode** | timeline/preview | There is no ruler at all; the only time display is `format!("{:.2}s / {:.2}s")` (editor_view.rs:1756). The playhead is a 2px div redrawn inside each lane with no hit target, and the lane div has no mouse handler, so the playhead cannot be clicked or dragged anywhere in the app — the single most obvious missing thing a user hits in the first minute. Nothing quantizes to frames either: `advance_playback` (editor_view.rs:754-775) adds a float wall-clock delta, and arrow keys/transport seek ±1 **second** (L2069-2076). Palmier's playhead is an Int frame throughout, TimelineRuler draws an adaptive ~80px tick ladder with monospaced timecode, and ruler mouse-down starts a scrub that pauses playback, seeks in `interactiveScrub` mode, auto-scrolls near the viewport edge and re-seeks exact on release. Also add the scrub bar under the viewer and a reduced-quality scrub tier (half-res / skip effect passes while scrubbing), which our per-frame render architecture can do cheaply. |
| M | **Timeline scroll container, cursor-anchored zoom, pinned track headers** | timeline | The lane is `.relative().flex_1().overflow_hidden()` (editor_view.rs:1992-1999) with no scroll container, so once you zoom in past the viewport everything beyond it is simply unreachable — zoom is currently a trap. Zoom itself is two ×1.5 buttons clamped 8..400 px/s with no wheel or pinch handling and no scroll-to-playhead. Palmier puts the timeline in an NSScrollView with computed content size, Option+scroll zooming exponentially anchored to the frame under the cursor, pinch via magnify(), Cmd+scroll to pan, and applyPlayheadAnchoredScroll on zoom changes. Track headers must move outside the scrolled region — our track_row currently interleaves header and lane in the same flex row. |
| M | **Snapping (clip edges, playhead, sticky hysteresis, indicator)** | timeline | `finish_drag` (editor_view.rs:461-496) converts `delta_px / pixels_per_second` straight to ticks; `DragState` (L32-39) has no snap state and no snap-target collection exists anywhere in the crate. Palmier's pure SnapEngine collects every non-dragged clip start/end plus the playhead and beat markers, tests multiple probe offsets simultaneously (all selected clips' starts AND ends), widens the threshold for the playhead, keeps sticky state until the cursor moves 2.5× the threshold away, and returns a pixel X for the indicator overlay — wired into move, trim-left, trim-right, range-drag and razor-hover. Do not reinvent: apps/web already has element-snap-source, playhead-snap-source, group-move/snap, snap-indicator and a `snappingEnabled` toggle; port that and check it against palmier's sticky multiplier, per-target-kind thresholds and multi-probe. Keep the planner in opencut-core so it is unit-testable like view_model.rs. |
| L | **Multi-clip selection, cross-track drag, and overwrite/collision resolution** | timeline | Three tightly-coupled holes that together make timeline editing feel broken. (a) `begin_drag` (editor_view.rs:508) unconditionally calls `editor.select(vec![reference])` — no shift-click, no marquee (the lane div has no listener at all, so clicking empty space does nothing), and every consumer uses `selection().first()`. The core is already multi-capable (`Command::SetSelection {elements: Vec<ElementRef>}`, clipboard::copy over the whole selection), so this is purely a UI gap. (b) `ElementRef` embeds the track id and `DragState` has no track field, so a clip can never leave its track — palmier resolves cursor Y into a TrackDropTarget (existing track or inter-track insertion zone), draws an insertion line and ghost, and clamps the track delta until every non-pinned mover lands on a compatible track. (c) `AddElement` appends and `MoveElement` sets a start with no neighbour awareness (command.rs:552-602), so two elements on the same track overlap indefinitely and both composite — palmier's pure OverwriteEngine.computeOverwrite returns remove/trimEnd/trimStart/split actions and runs on every add, move and widening trim. Needs a `MoveElements` multi-element command and a pure overwrite.rs planner. |
| M | **Audio basics: video-clip audio, per-clip volume/mute, keyframable gain, fades, track/master gain** | audio | Four gaps that make audio unusable, all in the model. `VideoElement` (element.rs:105-119) has no volume/muted field and `start_audio` only iterates `scene.tracks.audio` matching `Element::Audio(..)`, so a video clip's audio is silent in preview and export — palmier's CompositionBuilder inserts an audio composition track for every clip that has one. `AudioElement` carries a single `volume: f32` and is uniquely missing an `animations` field, so volume cannot be keyframed by construction, and there is no SetVolume command at all so gain is not even settable or undoable. There are no fade fields, so every cut clicks (palmier additionally applies a 144-frame equal-power fade at every scrub grain boundary). `Track` (track.rs:18-27) has hidden/muted but no volume or solo, and there is no master gain — while `mix_stereo` just hard-clamps the sum to ±1, so overlapping clips clip audibly with no indication. Land these together so one mixer path composes clip gain × fade × track gain × master. apps/web has the whole design already (clampDb, dBToLinear, buildAudioGainAutomation, VOLUME_DB_MIN/MAX, a draggable volume line, and a proper -1 dBFS master limiter in src/media/audio-mastering.ts). |
| XL | **Rewrite audio playback as a streaming mixer** | audio | The current design is a structural dead end, not a slow implementation. On Play we synchronously ffmpeg-decode each referenced media in full on the GPUI thread and mix the entire remaining timeline into one Vec<f32> for a rodio sink (editor_view.rs:204-300). Six measured consequences: the Play button stalls for seconds on first press per media; the mix buffer alone is ~352 KB per timeline second (~210 MB for a 10-minute timeline) on top of an unbounded never-evicted PCM cache; the mix is frozen at Play time so any volume/mute/move edit is inaudible until stop/start; scrubbing is completely silent; `advance_playback` moves the playhead on wall-clock `Instant` deltas while rodio plays off the device clock, so A/V drift accumulates with no resync path; and nothing can observe sample levels, so meters and waveform-under-playhead are impossible. Palmier's ScrubAudioEngine keeps windowed 48 kHz stereo PCM (96k-frame windows, LRU 256) and serves 2400-frame grains with 144-frame edge fades off a dedicated userInteractive queue. Target architecture is closer to apps/web's audio-manager.ts (chunks scheduled against the audio clock with 2 s lookahead, per-clip gain automation) ported onto cpal/rodio's raw Source trait — grow that, do not grow mix_stereo. Also drive the playhead from the audio clock. |
| L | **Windowed video decode + texture reuse (clips over ~15s are wrong today)** | preview | `decode_video_clip` (opencut-preview/src/lib.rs:379-423) is one ffmpeg invocation per clip that pre-decodes the whole clip into RAM at a hardcoded 320×180/30fps and hard-caps at VIDEO_MAX_FRAMES = 450 — so any clip longer than ~15 seconds or wider than 320px simply does not render correctly, regardless of what the timeline says. Each displayed frame is then re-uploaded as a brand-new GPU texture (lib.rs:320-329). Replace with a seek + windowed streaming decoder and reuse one texture per element. Palmier gets this free from AVPlayer owning playback; we own it explicitly, which is the price of the portable stack. Note the zero-copy GPU→GPUI path stays blocked by GPUI-on-blade, so render-size adaptivity and the scrub quality tier are where the perf actually comes from. |
| L | **Export: destination picker, real options, audio muxed, off-thread job with progress/cancel, atomic staging** | export | Every part of export is currently wrong. Output paths are compile-time constants (`~/vii-export.mp4`, `~/vii-frame.png`, editor_view.rs:105-112), so every export silently clobbers the same two files — and rfd is already a dependency used for import, so `save_file()` is near-drop-in. There is no ExportOptions type at all; args are hardcoded `-pix_fmt yuv420p` with no codec/bitrate/quality, and the caller force-scales to max 1280px wide (editor_view.rs:664-666) so a 1080p project always exports 720p. No audio stream is ever opened, so every exported MP4 is silent even though the timeline plays back mixed. The call is `let _ = renderer.export_video(...)` on the GPUI thread — UI frozen for the whole encode, result discarded, no progress, no cancel, no error. And ffmpeg writes straight to the final path, so an aborted export leaves a truncated file where a good one was. Palmier has ExportOptions (format/codec/resolution presets with size estimates), a serial ExportQueue with per-job status and cancel, and `withStagedOutput()` writing to a `.partial` sibling then committing with replaceItemAt. Cheapest audio route: mix_stereo to a temp WAV as a second ffmpeg input with `-c:a aac -shortest`; the real fix shares one mix graph between preview and export so envelopes cannot diverge. |
| L | **Real project files: package, Save As/Open, schema version, atomic write, surfaced errors, recents** | project/app-shell | The whole project is one `serde_json::to_string_pretty` blob at the fixed path `~/vii-project.json` (editor_view.rs:101, 838-841) — there is exactly one project, ever. Three specific defects on top: the write is a bare `std::fs::write` with no temp-and-rename, so a crash mid-save destroys the project; `Project` has no version field (project.rs:9-16 is `ProjectMetadata{id,name}`), so any model change silently fails to deserialize — and every item in this roadmap changes the model; and Load swallows the error entirely (`if let Ok(project) = serde_json::from_str::<Project>(&json)` with no else branch, L843-848), so the user clicks Load and nothing happens. Palmier's VideoProject is an NSDocument writing a `.palmier` directory package (project.json + media.json + thumbnail.jpg + media/), ProjectFile.decode() is an explicit versioned decode with a legacy fallback, and ProjectRegistry keeps a recents list with register-on-open and updateURL when a project moves. Also needs a macOS menu bar — we have no NSMenu at all, so there is no Save As, no Open Recent, no ⌘S/⌘O/⌘N. |
| L | **Canvas direct manipulation: click-to-select, move, resize** | preview | The preview is a non-interactive image: `img(ImageSource::Render(...))` in a fixed 512×288 div (editor_view.rs:1076-1163) with no `on_mouse_down`/`on_mouse_move` at all, and DragState is timeline-only. Clicking the preview does nothing, and transforms can only be changed through inspector ±steppers. Palmier has PreviewHitTester (aspect-fit content rect, text clips first, then video/image tracks, skipping hidden tracks and opacity ≤ 0.01, un-rotating the point into clip-local space and applying crop insets) plus TransformOverlayView (selection rect, 4 corner handles, applyTransform live / commitTransform as one named undo step, text clips resizing fontScale instead of the box). Put the hit test in view_model.rs (pure, testable). apps/web/src/preview/{hit-test.ts, element-bounds.ts, controllers/transform-handle-controller.ts} is a direct port target. |
| M | **Keyframe correctness: edits at the playhead must write a key, not the base value** | inspector | Live bug, reproducible in two clicks: keyframe a property with `kf_button("opacity")`, then press the Opacity `+` stepper and nothing changes on canvas. `transform_row` (editor_view.rs:1361-1384) unconditionally executes `Command::SetTransform`, which overwrites the base Transform — but `Element::sampled_transform` overlays the animation channel on top, so once a property is animated its stepper is silently inert. Palmier routes every inspector write through an animation-aware path (writeOpacity/writePosition/... check `track.isActive` and upsertKeyframe at the active frame instead). Pair this with per-property keyframe navigation and a stamp/unstamp toggle (palmier's `‹ ◇ ›` control: filled diamond when the playhead is on a key, click to remove; disabled with 'Move playhead inside the clip' when outside) — cheap once `has_key_at / prev_key / next_key` exist on AnimationChannel. Also note `Command::TrimElement` does not touch `animations` at all, so trimming desyncs keys; palmier's KeyframeTrack.rebased(by:fallback:) synthesizes a boundary key at frame 0. |
| L | **Keyframe lane UI (see, drag, delete) and per-key easing** | inspector | There is no visualization of keyframes at all — editor_view.rs:1544-1563 renders the literal string `"◇ keyframe (N animated):"` plus four add-only buttons, and `Command::RemoveKeyframe` (command.rs:113) exists but is never dispatched from any UI path, so a mis-added key is unremovable except by undo. And every animation is linear: `Keyframe {time, value}` has no easing field and `AnimationChannel::sample` hardcodes `a.value + (b.value - a.value) * fraction` (element.rs:38-68) — no ease, no hold/step. ### Wave 3 — Differentiators and polish

Everything here is genuinely valuable but none of it is why someone would abandon our editor in the first ten minutes. Two items stand out as unusually cheap relative to their wave: activating the masks crate (already written, tested and dead) and the pure planners (caption chunking, silence-removal, word-cut, audio sync correlation) which are dependency-free array math that ports almost verbatim.
